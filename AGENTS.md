# Working in this repository

## What to edit

- `skill/SKILL.md` and `skill/reference/*.md` are the source. Everything under `plugin/`,
  `.agents/` and `.claude-plugin/` is generated by `scripts/build.mjs` - never edit those
  files by hand; the generated Markdown carries a marker saying so.
- `nova-bot/` is the source of the NOVA bot, the robot the plugin shows above the prompt:
  `hooks/*.ts(x)` (a Claude Code hooks module), `types/index.d.ts` (its state contract,
  declared under the plugin name `nova`) and `assets/icon.png`. The build copies it into
  `plugin/` and names the module in `hooks/hooks.json`; generated code files carry a comment
  line saying so. The hooks-module API is early access: check the bot after Claude Code
  updates. It is decoration only - keep everything the kit needs working out of it.
- `scripts/build.mjs` is the only place that knows the adapter layouts (plugin manifest,
  hooks, `.mcp.json`, marketplace manifest).
- Versions live in git tags only, cut by semantic-release (`.releaserc.json`,
  `.github/workflows/release.yml`): `x.y.z-rc.N` from `main`, stable `x.y.z` from `release`,
  which only `.github/workflows/promote.yml` (or `git push origin <sha>:release`) moves.
  Never add a `version` to `package.json` or the manifests: without one, Claude Code versions
  the plugin by commit SHA, which is what makes every commit on a channel an update. Since
  commit types decide the next version, pick `feat`/`fix` versus `docs`/`chore` deliberately.
  How to cut and promote a release: `RELEASING.md`.

## Commands

```sh
pnpm install                 # once; Node 22 or newer, pnpm (npm works too)
pnpm build                   # skill/ + nova-bot/ -> plugin/; skill/ -> .agents/skills/nova/; marketplace.json
pnpm test                    # node:test suite, see below
pnpm lint:md                 # markdownlint-cli2
pnpm validate:plugin         # claude plugin validate, strict except the missing version (needs the Claude Code CLI)
pnpm validate:skill          # Agent Skills spec validator (needs uv)
pnpm check                   # all of the above, in CI order
```

Run `pnpm build` after every change under `skill/` or `nova-bot/` and commit the generated output together
with the source. CI regenerates and fails on any difference. We chose this over a bot that
commits generated files: no bot commits on PRs, and the generated diff is visible in review;
the cost is remembering to run the build, which the failing check reminds you of.

## Tests

| File | Checks |
| --- | --- |
| `test/generated.test.mjs` | generated output matches `skill/` and `nova-bot/` |
| `test/skill.test.mjs` | frontmatter, `name` equals the skill directory, description length, line count, reference links resolve, references one level deep, agent-neutral wording, no planned commands |
| `test/plugin.test.mjs` | manifest shapes, no pinned version, no reserved name prefixes, `userConfig` holds at most `host`, hook script behaviour, the NOVA bot module, no `bin/` |
| `test/secrets.test.mjs` | no token-like strings, private keys or instance hostnames anywhere |
| `test/commands.test.mjs` | every `nova <subcommand>` mentioned in the skill answers `--help` with its own usage (not a parent group's); skipped with a message when `nova` is not installed (CI installs the latest release) |

## Content rules

- Document only commands that exist in the released CLI. Mention planned commands at most
  once, in `SKILL.md`, and mark them as planned.
- Agent-neutral wording: "run `nova app list`", never the name of an agent's tool.
- `SKILL.md` stays under 500 lines; references are one level deep (`reference/*.md`, no
  subdirectories); every reference is linked from the routing table in `SKILL.md`.
- Safety rules (secrets, robot motion, destructive commands, untrusted data) come from the
  architecture decisions in the nova-cli repository (`docs/decisions`). Keep them when
  restructuring.
- No secrets, no instance or cluster hostnames, no personal names, no internal project
  names - the repository may become public.

## Conventions

- Conventional Commits (`feat(skill): …`, `fix(build): …`, `docs: …`, `ci: …`).
- Tooling is Node with no runtime dependencies and `node:test`; the external validators
  (`claude`, `markdownlint-cli2`, `agentskills`) are npm or uvx tools, so one toolchain covers
  everything. Keep it that way unless a dependency buys something the tests cannot do.
- `evals/` holds cases for `claude plugin eval`; they call a model, so they are not part of
  CI. Run them locally with `claude plugin eval plugin --eval-dir evals --trust-plugin`.
